# 原生游戏参考驱动重构计划

> 目标：让后续 AI 能按证据修复并完成 12 款原生游戏的交互重构。此计划记录当前可核实状态、工作分区、执行顺序和验收条件。计划本身不代表代码重构或设备验收已完成。

## 一、目标与完成定义

对 12 款游戏逐项对照成熟项目的实际源码、官方文档和玩法资料，改进本项目的触摸交互、状态流、反馈、存档恢复和目标平板布局。

每款游戏完成时必须同时满足：

1. 有与本游戏直接相关的 20–30 份真实读取资料；记录具体文件/页面、读取证据、许可、适用点、本项目对应代码和差距。通用资料可共享，但不可用同一批泛化文章重复填满每款计数。
2. 参考结论落实到本地行为或明确解释为何不采纳；不以增加动效、行数或资料条目数量代替重构。
3. 本局关键状态在操作后自动保存；关闭、暂停、失焦、回大厅和重新打开时可恢复。
4. Godot 4.7.2 项目上下文解析通过。未做的运行、设备和性能验收必须标为未验证。
5. 不引入联网对战、运行时 AI 或与产品约定冲突的玩法；不擅自构建或发布 APK。

## 三、执行顺序

### 阶段 0：建立基线和变更边界

1. 所有接手者先读根目录 `AGENTS.md` 与本计划，再读自己负责的现有文件；不得只依据旧代理摘要直接覆盖。
2. 本地工作区没有可用的 Git 仓库状态，不能依赖 `git diff` 还原变更。编辑前在任务记录中列出将修改的精确文件；多人并行时严格按下方目录分工。
3. 先用现有代码和研究 JSON 把问题写成“触发条件 → 影响 → 根因 → 修复目标 → 验证方法”。没有可复现代码证据的问题标为待验证，不直接改。

### 阶段 1：完成参考质量审计

1. 对 12 款逐款计算：真实唯一来源数、同项目不同文件数、共享来源数、失败/排除数、直接相关数。
2. 每条来源最少记录：标题、稳定 URL 或仓库提交、文件路径、许可、读取状态、正文/源码证据摘录或行范围、具体交互结论、本项目对应文件/函数、差距、状态。
3. 将来源标为“核心交互直接相关 / 共用触控或无障碍原则 / 弱相关背景”。每款 20–30 目标以直接相关资料为主；共用资料单独展示，不重复充作每款的专属依据。
4. 删除或降级不相关的 AI、测试、纯绘制、营销页等条目；不足时继续实际读取合适资料。读取失败的 URL 不计数。
5. 修正 JSON 口径，尤其策略文件没有 `sourceId` 时不得宣称 source ID 唯一；哈希仅在本地重算确认后才描述为已校验。
6. 更新三份 benchmark 笔记，形成“参考结论 → 本地现状 → 修复项 → 状态”清单。

## 四、三个并发接手者的工作指令

### AI 1：参考证据和差距矩阵

先审计 `content-src/research/*.json` 与三份 benchmark。逐款验证真实资料、文件路径、相关度、来源计数和本地映射；修正研究文件与笔记，不改产品代码。输出每款直接相关数、共用数、弱相关/排除数、缺口与许可限制。禁止把搜索摘要、失败抓取、同一文件的重复 URL 或共享背景资料当成专属资料填数。

### AI 2：棋类实现

只改阶段 2 A 组列出的代码文件。先阅读参考清单指向的源文件与当前实现，再按触摸、状态机、存档恢复的差距修复。记录每项修改的来源文件、项目函数和触发场景；不做截图、不构建 APK、不引入运行时 AI。完成后运行允许的 Godot 项目解析并报告设备验收仍需覆盖的场景。

### AI 3：答题、记忆/冒险/听读实现

按阶段 2 B/C 组分批执行，不能同时写同一文件；先选 B 或 C 作为第一批，完成并解析后再接下一批。每个修复必须由本游戏直接相关参考支撑；保持内容规则、儿童年龄难度和自动保存要求。优先修复可证明的状态恢复、输入锁、答案泄露和语义操作差距，不为动效而动效。

### 集成负责人：共享 UI、音频和存档

游戏簇提交后独占阶段 2 D 组共享文件。处理弹窗、滚动、音量、焦点和统一返回流程；对同一输入只保留一条有效事件链。串行集成各游戏簇后执行项目解析并记录输出。

|---|---|
| 参考证据 | URL、仓库提交、文件路径、实际读取段落/函数 |

| 验证 | Godot解析 / 静态状态流 / 设备手测，分项记录 |
| 状态 | 已实现、解析通过、设备验证通过、未验证；禁止合并成单一“完成” |
